# Shell Features Reference

This document lists every shell feature and whether it is supported (✅) or blocked (❌).
Blocked features are rejected before execution with exit code 2.

The in-shell `help` command mirrors these feature categories: run `help` for a concise supported/unsupported summary plus allowed and selectively elevatable commands, or `help <feature|command>` for details about a specific feature or command.

## Builtins

- ✅ `awk [-F SEP] [-v NAME=VALUE] ['PROGRAM'|-f PROGRAM-FILE] [FILE]...` — practical POSIX-oriented text processing with BEGIN/main/range/END rules, fields, scalars, associative arrays, POSIX-oriented regex, control flow, user functions, `print`/`printf`, and common string builtins. Input files honor `AllowedPaths`; evaluated expressions, strings, records, rules, statements, loop iterations, function calls/depth, regex work, substitution metadata, and stdout are bounded. awk programs cannot execute commands: `system()`, every form of `getline`, `close()`, and command pipes are rejected, as are file-output redirection and GNU-only features such as `gensub`, `asort`/`asorti`, `strtonum`, `IGNORECASE`, the third `match` argument, GNU boundary escapes, malformed-UTF-8 byte matching, and nondecimal source literals. Exact cross-implementation `printf`/numeric edge compatibility, including NaN/infinity spellings and uncommon flag combinations, is also outside the profile. Run `awk --help` for the exact profile.
- ✅ `break` — exit the innermost `for` loop
- ✅ `cat [-AbeEnstTuv] [FILE]...` — concatenate files to stdout; supports line numbering, blank squeezing, and non-printing character display
- ✅ `cd [-LP] [-|DIRECTORY]` — change the shell's working directory; targets must lie inside `AllowedPaths`; with no operand changes to `$HOME`, with `-` swaps to `$OLDPWD` (printing the new path); `-L` (default) preserves symlinks, `-P` resolves them; `-e`, `-@`, `CDPATH`, `~user` not supported
- ✅ `continue` — skip to the next iteration of the innermost `for` loop
- ✅ `cut [-b LIST|-c LIST|-f LIST] [-d DELIM] [-s] [-n] [--complement] [--output-delimiter=STRING] [FILE]...` — remove sections from each line of files
- ✅ `df [-hHkPTialx] [-t TYPE] [-x TYPE] [--total] [--no-sync]` — report file system disk space usage (Linux/macOS only; on Windows `df` exits 1 with `df: not supported on this platform` because mount enumeration goes through `/proc/self/mountinfo` on Linux and `getfsstat(2)` on macOS, neither of which has a Windows equivalent); Linux reads `/proc/self/mountinfo` directly via `os.Open`, bypassing `AllowedPaths`; positional `FILE` operands and `--sync`, `-B`, `--output` are not supported; mount table capped at 100 000 entries
- ✅ `du [-asScSLP0bhkm] [-d N] [--apparent-size|--si] [FILE]...` — estimate file space usage; recursion capped at depth 256 and hardlink-dedup tracking capped at 2²⁰ entries; `--files0-from`, `--exclude-from`/`-X`, `--exclude` are rejected (data-exfiltration / file-driven control); `-B`/`--block-size`, `-t`/`--threshold`, `-x`/`--one-file-system`, `--inodes`, `--time`, `-l`/`--count-links` are not implemented
- ✅ `echo [-neE] [ARG]...` — write arguments to stdout; `-n` suppresses trailing newline, `-e` enables backslash escapes, `-E` disables them (default)
- ✅ `exit [N]` — exit the shell with status N (default 0)
- ✅ `false` — return exit code 1
- ✅ `find [-L] [-P] [PATH...] [EXPRESSION]` — search for files in a directory hierarchy; supports `--help`, `-name`, `-iname`, `-path`, `-ipath`, `-type` (b,c,d,f,l,p,s), `-size`, `-empty`, `-newer`, `-mtime`, `-mmin`, `-perm`, `-maxdepth`, `-mindepth`, `-print`, `-print0`, `-exec CMD {} \;`, `-execdir CMD {} \;`, `-prune`, `-quit`, logical operators (`!`, `-a`, `-o`, `()`); blocks `-delete`, `-regex` for sandbox safety
- ✅ `free [-h]` — report host memory and swap usage; a narrow read-only investigation snapshot, not a remediation or repeated-sampling command (see planned `vmstat`); Linux only, reads `/proc/meminfo` directly via `os.Open`, bypassing `AllowedPaths` (on macOS/Windows `free` exits 1 with `free: not supported on this platform` because neither exposes the buffers/cache/shared breakdown through a syscall this shell can call without cgo); `-h`/`--human` prints IEC binary sizes (e.g. `1.5Gi`); `-b`/`-k`/`-m`/`-g`/`--si`/`-w`/`-t`/`-s`/`-c` (repeated sampling) are not supported
- ✅ `grep [-EFGivclLnHhoqsxw] [-e PATTERN] [-m NUM] [-A NUM] [-B NUM] [-C NUM] PATTERN [FILE]...` — print lines that match patterns; uses RE2 regex engine (linear-time, no backtracking)
- ✅ `head [-n N|-c N] [-q|-v] [FILE]...` — output the first part of files (default: first 10 lines); `-z`/`--zero-terminated` and `--follow` are rejected
- ✅ `help [--all] [feature|command]` — display rshell features, a concise unsupported-feature summary, commands available in the current mode, allowlisted commands that require remediation mode, commands disabled by the `AllowedCommands` policy, the configured `AllowedPaths` sandbox roots grouped by read-only and read-write access, and the effective `AllowedSystemServices` unit/action grants in `UNIT:ACTION[+ACTION...]` form (with explicit default-deny notices when either policy is empty); remediation-required commands always include descriptions, while `--all` adds descriptions to commands disabled by policy; in read-only mode configured non-read grants remain visible but are marked inactive; with a topic, show detailed help for that feature or command
- ✅ `ip [-o|-4|-6|--brief] addr|link [show] [dev IFNAME]` — show network interface addresses and link-layer info (read-only); write ops (`add`, `del`, `flush`, `set`), namespace ops (`netns`, `-n`), and batch mode (`-b`/`-B`/`--force`) are blocked
- ✅ `ip route [show|list]` — show IPv4 routing table (Linux only; reads `/proc/net/route` directly via `os.Open`, bypassing `AllowedPaths`); at most 10 000 entries loaded; lines longer than 1 MiB abort parsing with an error (exit 1)
- ✅ `ip route get ADDRESS` — show the route selected by longest-prefix-match for ADDRESS (Linux only); write ops (`add`, `del`, `flush`, `replace`, `change`, `save`, `restore`) are blocked; `-6` (IPv6 routing) is not supported
- ✅ `journalctl (-u SERVICE...|-k) [-b] [-n COUNT] [--since TIME] [-o short|cat]` — bounded journal investigation for exact system services or current-boot kernel messages; defaults to 100 and caps at 1,000 entries, 32 service scopes, and 64 KiB per selected field; `short` sanitizes controls, non-graphic Unicode, and invalid UTF-8 and labels unidentified kernel entries `kernel`, while `cat` matches host `journalctl` within the field bound by writing each `MESSAGE` value unchanged and appending one newline; service reads require exact `SERVICE:read` grants and kernel reads require `systemd-journald.service:read`; also supports `--disk-usage` with `systemd-journald.service:read`, plus remediation-only `--rotate`, `--vacuum-size SIZE`, `--vacuum-time AGE`, and `--dry-run` with `systemd-journald.service:clean`; time-only vacuum removes every eligible archive at least `AGE` old, while size vacuum targets the total allocated journal storage reported by `--disk-usage` (active plus archived, matching host `journalctl --vacuum-size`), requires `AGE` as a minimum deletion age, never deletes active journals or newer archives merely to reach its target, and reports the remaining allocated bytes when the target is still exceeded; rotation may precede vacuuming, while `--dry-run` cannot rotate; bare/unrestricted reads, globbed services, arbitrary matches, follow mode, raw structured output, alternate sources, cursors, machines, namespaces, and arbitrary boot selection are unavailable; log reads use a bounded pure-Go parser for regular/compact and XZ/LZ4/Zstandard journal files with no host `journalctl`, cgo, or libsystemd dependency; rotation requires Linux with procfs descriptor links at `/proc/self/fd`, and mounted-file usage/vacuum operations support Linux/macOS
- ✅ `jq [-hcernsR] [--arg NAME VALUE] [--argjson NAME JSON] [FILTER] [FILE]...` — self-contained jq 1.8 subset supporting fields, indexes, iteration, `?`, pipes, generators, literals, constructors, variables, comparisons, boolean operators, `//`, arithmetic, and `select`, `map`, `length`, `keys`, `has`, `type`, `not`, and `empty`; an omitted filter is identity. Up to 64 operands are accepted as identity-verified regular files through `AllowedPaths`; special files and descriptor portals are rejected. Limits include 64 KiB/4,096 nodes per filter, 8 MiB cumulative input, 1 MiB raw lines, 64-level/65,536-node/4-MiB values, 100,000 evaluation steps, 10,000 results, 131,072 retained nodes/8 MiB of evaluator state, 1 MiB output, and 64 variable bindings/1 MiB of binding text. Evaluation budgets are cumulative and fail hard. Assignments, user-defined functions, reduce/foreach, try/catch, regex, recursion, modules, environment access, file-based filters/variables, streaming, dates, formatters, `as`, conditionals, slices, array-index-by-array, and `$__loc__` are unavailable; number and per-value-limit differences are documented below
- ✅ `logrotate (-s SIZE|-f) [-n] [-v] FILE...` — remediation-mode helper that truncates log files to zero bytes through `AllowedPaths`; `--size SIZE` truncates only files at least SIZE bytes, `--force` explicitly truncates without a threshold, `--dry-run` reports without modifying files, and `--verbose` reports per-file actions. Symlinked write targets are rejected with `symlinks are not supported as write targets`, and, on Unix, hard-linked targets (link count > 1) with `hard links are not supported as write targets` — not enforced on Windows, where no link count is available from an open handle; pass the real, single-linked log path instead. This is not a full `logrotate(8)` replacement: no config parsing, rename-based rotation, retained copies, compression, state files, or rotate scripts.
- ✅ `lsof [-p PIDLIST] [-c NAME] [-u UIDLIST] [-a]` — list open files, with emphasis on files still open after being deleted (Linux only; on macOS/Windows `lsof` exits 1 with `lsof: not supported on this platform`); reads `/proc/<pid>/fd/*` metadata (COMMAND/PID/USER/FD/TYPE/DEVICE/SIZE/NODE) directly via `os.Readlink`/`unix.Stat`, bypassing `AllowedPaths` like `ss`/`df`/`free`, but the resolved NAME path is checked against `AllowedPaths` and replaced with `(restricted)` (or `(restricted) (deleted)`) when outside every configured root: a deliberate divergence, since NAME can point anywhere on the host filesystem; `-p` selects by PID list, `-c` by command-name prefix (literal), `-u` by numeric UID list, `-a` ANDs the selectors instead of the default OR; network detail (`-i`/`-U`/`-s`/`-T`/`-n`/`-P`), directory-tree scans (`+d`/`+D`), repeat mode (`+r`/`-r`), device-cache files (`-D`/`-f`/`+f`), and login-name UID resolution are not supported
- ✅ `sort [-rnhubfds] [-k KEYDEF] [-t SEP] [-c|-C] [FILE]...` — sort lines of text files; `-h`/`--human-numeric-sort` orders by SI suffix (none < K/k < M < G < T < P < E < Z < Y < R < Q) then by numeric value (single-letter suffixes only — `Ki`, `Mi`, etc. are not recognised); `-o`, `--compress-program`, and `-T` are rejected (filesystem write / exec)
- ✅ `ss [-tuaxlans4689Hoehs] [OPTION]...` — display network socket statistics; reads kernel socket state directly via `os.Open` (bypassing `AllowedPaths`) from: Linux: `/proc/net/`; macOS: sysctl; Windows: iphlpapi.dll; `-F`/`--filter` (GTFOBins file-read), `-p`/`--processes` (PID disclosure), `-K`/`--kill`, `-E`/`--events`, and `-N`/`--net` are rejected
- ✅ `stat -f FILE...` — report filesystem status for each operand through `AllowedPaths`: filesystem ID/type, name-length limit, block sizes, total/free/available blocks, and inode totals; supported on Linux, macOS, and Windows, with unavailable platform fields rendered honestly (`Namelen: ?` on macOS and inode totals/free as `-` on Windows); ordinary file-status mode, custom formats, terse output, and cache controls are not implemented
- ✅ `systemctl [--system] [--no-pager] COMMAND [OPTION]... [UNIT]...` — remediation-mode-only bounded Linux system-manager inspection and control for exact, fully suffixed unit names; every invocation, including `--help`, bare/list/status inspection, and mutations, fails before grant lookup or manager access in read-only mode; once enabled, a bare invocation is restricted `list-units`, which supports `--all`, `--type`, `--state`, and `--no-legend` but considers only units with exact `read` grants; by default it returns already-loaded units that are active, failed, or carrying a job, while `--all` may load valid read-granted candidates and includes inactive units (nonexistent names may be omitted); the supported command set is exactly `list-units`, `status`, `start`, `stop`, `reload`, `restart`, `enable`, and `disable`; listing and status require exact `read` grants, and each mutation requires its matching exact action grant for every operand before any effect; runtime jobs use fixed `replace` mode, process multiple anchors sequentially in operand order, and may act on dependency-related units through normal systemd transaction semantics; enable/disable may follow `[Install] Alias=`, `Also=`, and template `DefaultInstance=` into auxiliary unit-file changes, then globally reload the manager, which may run generators and pick up unrelated host changes; granted unit payloads, install metadata, aliases, and dependency graphs are operator-trusted, so dedicated lifecycle verbs being absent does not make lifecycle effects impossible through a granted unit; every manager-backend operation has a fixed 30-second cap in addition to the runner deadline; accepts `.service`, `.timer`, `.socket`, and other valid unit types, with at most 32 operands and 64 KiB per returned field; `status` omits process command lines, logs, arbitrary properties, unit-file paths, and D-Bus object paths, and every human-readable field is sanitized; `show`, the `is-*` predicates, conditional restart variants, `reset-failed`, `--now`, arbitrary enumeration/properties, globs, implicit `.service`, user/machine/root/image targets, `clean`, standalone `daemon-reload`, `kill`, unit-file editing/linking/masking/presets, dedicated power-management verbs, asynchronous jobs, arbitrary job modes, and explicit dependency-expansion switches are unavailable; requires procfs descriptor links at `/proc/self/fd` and uses the configured public system D-Bus socket without executing host `systemctl`
- ✅ `ls [-1aAdFhlpRrSt] [--offset N] [--limit N] [FILE]...` — list directory contents; `--offset`/`--limit` are non-standard pagination flags (single-directory only, silently ignored with `-R` or multiple arguments, capped at 1,000 entries per call); offset operates on filesystem order (not sorted order) for O(n) memory
- ✅ `ntfs-du [--apparent-size] [--top-files N] [--top-ext N] [-d N] [--tree-limit N] [--min SIZE] [--exclude PATH]... [--find-ext CSV|--find-glob PAT|--find-regex RE]... [--find-limit N] [--output json] [FOLDER]` — quickly find large folders, files, and file extensions across an NTFS volume by reading the raw `$MFT`, so runtime scales with the volume's file count rather than the starting folder (use `du` for a small subtree); `--find-ext`/`--find-glob`/`--find-regex` locate specific files, and `--top-ext`/`--find-ext` support extensions of any length (**Windows only** — registered only on Windows, absent elsewhere; **requires Administrator**; NTFS volumes only); opens the raw volume device `\\.\<drive>:` directly, bypassing `AllowedPaths` (same trade-off as `ss`/`df`/`ip route`) and reporting names/sizes across the whole volume regardless of sandbox roots; scans the current drive root by default (depth 1, at most 100 tree nodes, top-10 files and extensions, `--min` 100M); `--tree-limit` caps emitted tree nodes at 1,000 and `--top-ext` caps extension results at 64; emits JSON only (`--output json`; a human-readable format is planned)
- ✅ `ping [-c N] [-W DURATION] [-i DURATION] [-q] [-4|-6] [-h] HOST` — send ICMP echo requests to a network host and report round-trip statistics; `-f` (flood), `-b` (broadcast), `-s` (packet size), `-I` (interface), `-p` (pattern), and `-R` (record route) are blocked; count/wait/interval are clamped to safe ranges with a warning; multicast, unspecified (`0.0.0.0`/`::`), and broadcast addresses (IPv4 last-octet `.255`) are rejected — note: directed broadcasts on non-standard subnets (e.g. `.127` on a `/25`) are not blocked without subnet-mask knowledge
- ✅ `pmap [-x] [-h|--help] PID...` — report per-process virtual memory mappings (start address, size, permission mode, mapping label); Linux reads `<ProcPath>/<pid>/maps` (or `smaps` for `-x`) directly via `os.Open`, bypassing `AllowedPaths` (the configured proc root is trusted and the remaining path is derived only from the numeric PID); Windows enumerates committed regions via `VirtualQueryEx` and labels each by its `MEMORY_BASIC_INFORMATION` type rather than a resolved file path (`-x` exits 1 with `pmap: -x is not supported on this platform`, since Windows has no per-region RSS/Dirty breakdown without a working-set walk); macOS enumerates regions via the `proc_pidinfo(PROC_PIDREGIONINFO)` kernel call reached through the raw `syscall.SYS_PROC_INFO` trap (`-x` also exits 1 with `pmap: -x is not supported on this platform`, since `proc_regioninfo` reports whole-shadow-chain resident/dirty counts rather than the private Rss/Dirty split pmap's extended columns expect); the process header shows only the comm/executable name, never argv; full-path, device, range, raw-kernel-name, rc-file read/write, extra-extended, quiet, and version flags are not supported
- ✅ `ps [-e|-A] [-f] [-p PIDLIST] [-o FORMAT] [--sort SPEC]` — report process status; default shows current-session processes; `-e`/`-A` shows all; `-f` adds UID/PPID/STIME columns; `-p` selects by PID list; repeatable `-o`/`--format` accepts the canonical fields `pid`, `ppid`, `uid`, `state`, `tty`, `stime`, `time`, `comm`, `rss`, `vsz`, `pmem`, `pcpu`, and `etime`, with `%cpu` and `%mem` as aliases for `pcpu` and `pmem`; `--sort` accepts the same fields and aliases in a comma- or space-separated list with optional `+` (ascending) or `-` (descending) prefixes; `pcpu` is the lifetime average since process start, not an interval measurement; unavailable requested metrics render as `-`; process names are comm-only, argv/environment/executable-path selectors are rejected, and process argv and environment are never read; on macOS, `stime`/`etime` remain available while `rss`/`vsz`/`pmem`/`time`/`pcpu` may be unavailable for processes the caller cannot inspect; on Windows, `rss`/`vsz` use the compatibility-sensitive `SystemProcessInformation` snapshot API and may be unavailable if it fails (`pmem` is then unavailable too)
- ✅ `printf FORMAT [ARGUMENT]...` — format and print data to stdout; supports `%s`, `%b`, `%c`, `%d`, `%i`, `%o`, `%u`, `%x`, `%X`, `%e`, `%E`, `%f`, `%F`, `%g`, `%G`, `%%`; format reuse for excess arguments; `%n` rejected (security risk); `-v` rejected
- ✅ `pwd [-LP]` — print the absolute pathname of the current working directory; `-L` (default) prints the shell's tracked logical path, `-P` resolves all symlinks; `-P` is best-effort within the sandbox (path components above `AllowedPaths` pass through unresolved); `--version` rejected
- ✅ `read [-r] [-p PROMPT] [-d DELIM] [-n N] [-N N] [-t SECS] [NAME...]` — read one delimited chunk from stdin and assign each IFS-split field to a shell variable (defaulting to `REPLY` when no NAME is given); `-n`/`-N` are capped at 1 MiB; non-raw mode treats `\<newline>` as a line continuation (both characters are dropped) and `\<X>` for any other `X` (including the active custom delimiter under `-d`) as a literal `X` with the backslash removed — e.g. `printf 'a\,b,c' | read -d , x` assigns `x="a,b"`; `-p` is suppressed unless stdin is a terminal (matches bash); `-a` (array), `-s` (silent), `-u` (read from FD), `-e` (readline), and `-i` (initial text) are not implemented
- ✅ `rg [-Fisv] [-e PATTERN] [-w|-x] [-nN] [-HI] [-o] [-c] [-l|--files-without-match] [-q] [-m NUM] [-A NUM] [-B NUM] [-C NUM] [-a] [-g GLOB] [--hidden] [--files] [--no-config] PATTERN [PATH]...` — recursively search directories for a regex pattern, a native re-implementation of ripgrep's common CLI surface (never executes the ripgrep binary); see the sub-bullets below for exact flag/edge-case semantics
  - **Basics:**
    - With no PATH, searches the current directory recursively, or standard input when piped/redirected.
    - A `PATH` that is a directory is walked recursively, always showing the file path prefix, while a single explicit file operand omits it unless `-H` is given.
    - Uses RE2 regex engine (linear-time, no backtracking).
  - **Symlinks, hidden files, and traversal limits:**
    - `-g`/`--glob` and `--hidden` provide simple gitignore-style include/exclude filtering and dotfile visibility, but `.gitignore`/`.ignore`/`.rgignore` files are not consulted.
    - Explicit file/directory operands follow symlinks (read operations follow symlinks by design), but directory traversal never follows symlinks.
    - Each directory level is capped at 1,000,000 entries (a warning is emitted and the level is truncated beyond that).
    - Once `--hidden` has independently allowed traversal to reach a hidden entry's contents, normal glob filtering still applies to those contents.
  - **Glob (`-g`/`--glob`) matching:**
    - `-g`/`--glob` patterns are syntax-checked up front, so a malformed glob (e.g. an unclosed `[` character class) is reported as an error (exit 2) rather than silently matching nothing, and blocks explicit file operands too, not just directory traversal.
    - A directory is pruned or re-admitted by whichever glob given later matches it (an earlier `!foo/**` exclusion can be re-admitted by a later `foo/**` include), matching ripgrep's documented "glob given later takes precedence" rule.
    - A genuinely empty `-g` pattern (`-g ''`, as opposed to a bare `-g '!'`) is a complete no-op, exactly as if `-g` had not been given at all, matching ripgrep exactly — it does not flip the default file-visibility mode to "deny unless matched," since it can never match any nonempty path either way.
    - `**` in a glob matches zero or more whole path components in the MIDDLE or at the START of a pattern (e.g. `a/**/f.txt` matches both `a/f.txt` and `a/b/c/f.txt`, and `**/foo` matches a top-level `foo`), but a pattern ending in one or more trailing `**` segments (e.g. `a/**` or `.cache/**`) only matches paths strictly INSIDE the directory named by the preceding fixed segments — it never matches that exact prefix path itself (e.g. `-g 'a/**'` does not match a literal path `a`, only something like `a/x`), matching ripgrep exactly.
    - A gitignore-style negated character class inside a glob, e.g. `[!a]` (matches anything EXCEPT `a`, not literal `!` or `a`), is honored exactly like real ripgrep, whose own `-g` glob syntax follows gitignore conventions — translated internally before reaching Go's `filepath.Match`, which has no `!`-negation convention of its own and would otherwise treat `[!a]` as "match literal `!` or `a`", the OPPOSITE of gitignore's intent. Go's own `[^a]` negation syntax is also accepted by real ripgrep's glob engine and produces the identical result, so it needs no character-rewriting itself. Only the FIRST character immediately after an unescaped `[` is ever treated as the negation marker (matching gitignore's own rule): a `!` anywhere else inside the class (e.g. `[a!]`) is an ordinary literal member, and an escaped bracket (`\[...\]`, a literal `[`/`]`, not a character class at all) is left untouched.
    - A `]` as the FIRST member of a `[...]` class — negated (`[!]]`/`[^]]`) or POSITIVE (`[]a]`) — is a LITERAL class member under gitignore's own leading-`]`-is-literal convention, matching real ripgrep exactly on Linux/macOS (`[!]]`/`[^]]` match every one-character filename except `]`; `[]a]` matches filenames `]` and `a` both) — Go's `filepath.Match` has NO leading-`]`-is-literal convention at all, for a negated OR a positive class (`[^]a]` and even the plain positive `[]a]` are both syntax errors under Go), so the leading `]` is escaped (`\]`, the only way to express this in Go's syntax) internally rather than left bare. **Windows-only limitation**: Go's `filepath.Match` disables escaping entirely on Windows (a lone `\` there is its own path separator instead), so this rewriting is skipped there and any glob shaped like `[!]]`/`[^]]`/`[]a]` keeps its pre-existing rejection (exit 2) on Windows rather than trading it for a silently wrong match.
    - A `/` occurring INSIDE an unescaped `[...]` bracket character class (e.g. `[a/]`) is a literal class member, not a real path-component separator, matching real ripgrep exactly (`-g '[a/]'` still lists a file named `a`, since the class matches literal `a` OR literal `/`) — only a `/` OUTSIDE any bracket still splits the glob into path segments as usual (e.g. `-g 'sub/[x/]'` still correctly matches `sub/x`, splitting only at the real separator before the bracket). That bracketed `/` still disables the implicit "match at any depth" basename-matching scope a genuinely slash-free pattern gets, however, matching real ripgrep's own glob-compilation behavior exactly: in a tree containing both a top-level `a` and a nested `d/a`, `-g '[a/]'` lists only the top-level `a` (the pattern is anchored to match exactly one character against the WHOLE path, which the 3-character `d/a` cannot satisfy), whereas the slash-free `-g '[a]'` lists both.
    - Matching is computed with dynamic programming using only O(path depth) memory regardless of glob pattern length (not a full pattern-length×path-length table, and not naive backtracking), so neither a very long `-g` argument nor a pattern with many `**` segments against a long non-matching path can exhaust memory or cause combinatorial blowup.
    - `-g` patterns are additionally capped at 4,096 `/`-delimited segments (an intentional hardening divergence from ripgrep, which accepts arbitrarily many) so that even a pattern within the DP's memory bound cannot perform unbounded comparison work against every candidate path during traversal, and the SUM of segment counts across every `-g` flag in one invocation is separately capped at 4,096 total, so many individually-under-the-cap globs cannot restore the same unbounded per-candidate-path work.
    - A glob overrides the default hidden-entry skip exactly when it matches that hidden entry's OWN path directly, matching ripgrep exactly — this can be a `/`-containing glob, as long as it reaches the hidden entry exactly (e.g. with a visible `sub/` containing a hidden `sub/.h` or hidden directory `sub/.hiddendir/`, `-g 'sub/*'` reveals the hidden file and `-g 'sub/**'` reveals the hidden directory itself and everything inside it), but a glob that only matches something INSIDE an already-hidden entry, without matching that entry's own path (e.g. `.cache/**` against top-level hidden `.cache`, or `sub/.hiddendir/*` against nested hidden `sub/.hiddendir`), does not reveal it — the hidden entry itself must already be visible before matching descends further.
  - **Context (`-A`/`-B`/`-C`), `-m`, and output modes:**
    - `-A`/`-B`/`-C`/`-m` reject an explicit negative value instead of silently treating it as no context/unlimited, and `-A`/`-B`/`-C` are otherwise clamped to 1,000 lines.
    - `-m 0` means the file is never searched at all (not "confirmed zero matches"), producing no output and exit 1 uniformly, including under `--files-without-match`.
    - `-m`/`-l`/`--files-without-match`/`-q` otherwise stop reading a file's remaining input as soon as the result is determined, rather than scanning to EOF, though a match landing inside an already-open `-A`/`-C` trailing-context window from the limiting match is still printed with the same `-o`/`-v` formatting an ordinary matching line would get (matching ripgrep's documented "more contextual lines might be printed than the given limit" behavior).
    - `--files-without-match`'s (and `-q` combined with it) exit status reflects whether a file had no match, not whether the underlying scan found one, and `-q` also suppresses its filename output at EOF.
    - `-c` omits a file with zero matches from its output (ripgrep's separate `--include-zero` flag is not implemented).
    - `-o` does not suppress `-A`/`-B`/`-C` context (unlike GNU grep) and prints the whole line for a line selected by `-o -v`.
    - In normal line-output mode (not `-c`), scanning stops entirely after the first binary-file match, matching ripgrep.
    - Numeric-flag validation (`-m`/`-A`/`-B`/`-C` negative-value rejection) happens before the `--help` short-circuit, so e.g. `rg --max-count=-1 --help` still exits 2 rather than printing help.
    - A pattern (regex or, for a literal raw newline byte, `-F` fixed-string) whose every possible match requires a literal newline character (e.g. bare `\n`, `[\n]`, or a concatenation/group/mandatory-repetition containing one) is rejected with exit 2 and ripgrep's own message, since a per-line scanner can never satisfy it and `-U`/`--multiline` is not implemented — a pattern that CAN match something else (a negated class, a class containing `\n` among other characters, or an alternation with at least one non-newline-requiring branch) is accepted normally. This rejection also applies when the newline-only sub-expression is wrapped in an OPTIONAL or repeated quantifier whose max bound is still >=1 (`\n?`, `\n*`, `\n{0,3}`, `[\n]?`, etc.), matching ripgrep exactly: the quantifier's own min bound (including a min of 0) does not change what the quantified body itself denotes, so a pattern like `\n?` is rejected even though its own zero-repetition match would not itself consume a newline. An EXACT zero repetition (`\n{0}`/`\n{0,0}`, as opposed to `\n{0,1}`/`\n{0,3}`), in contrast, is accepted: it can NEVER consume a newline under any permitted count, since the only permitted count is zero — matching real ripgrep exactly, which also accepts both forms. This rejection is also re-checked AFTER Unicode code point escape translation, not just on the original pattern text: a newline encoded as `\u000A`, `\u{A}`, or `\U0000000A` (all decoding to U+000A LINE FEED) is rejected the same way, since it is not valid Go regex syntax on its own (so the FIRST, pre-translation check cannot see it) but does compile successfully once translated to Go's own `\x{A}` form.
    - A line whose content is exactly `MaxLineBytes` (1 MiB) long is matched normally, not rejected as "too long" (the scanner's internal buffer is sized one byte larger than the cap, since `bufio.Scanner` needs room for the trailing delimiter byte in addition to the line's content before it can recognize and strip it).
    - A NUL byte occurring past the initial 64 KiB binary-detection probe, inside a single line longer than `MaxLineBytes` (1 MiB, with no newline) — whether within the scanner's own buffer cap or up to a further 64 MiB beyond it — is still recognized as a binary file and silently skipped for a recursively DISCOVERED file, matching real ripgrep exactly (tracked independently of the line scanner's own splitting: once the scanner's internal buffer gives up at `MaxLineBytes`+1 bytes with no delimiter found, reading continues directly from the underlying byte stream, bypassing the scanner, purely to keep searching for a NUL further into the same still-oversized line) — an EXPLICIT file/stdin operand does not get this same treatment and instead keeps the existing "line too long" error, since real ripgrep has no line-length cap at all and might have found a match occurring BEFORE the NUL within that same too-long line, which this implementation cannot recover once the line has grown past the cap; silently reporting no match in that case would risk a false negative, so the louder error is kept for that narrower case. A too-long line with no NUL at all within that combined search window is unaffected either way (still this implementation's own memory-safety error, since ripgrep itself has no line-length cap).
    - A carriage return immediately before a line's newline is preserved as ordinary line content, not stripped as part of the line-ending delimiter, matching ripgrep exactly (e.g. on a CRLF file containing `x\r\n`, `x$` does NOT match since the `\r` breaks the end-of-line anchor, while a literal `\r` pattern does match and output preserves the `\r`).
    - `-A0`/`-B0`/`-C0` (a context flag given but resolved to zero) is treated exactly like no context flag at all, including for the `--` group separator (verified directly: matching lines separated by a nonmatching line print consecutively under `-C0`, with no separator, unlike any positive context size on the same input).
    - The `--` context-group separator spans across files searched in the same invocation, not just between groups within one file (verified directly: `rg -A1 x a b`, two files each with one single-line match, prints a `--` separator between them; a nonmatching file given between two matching ones does not itself trigger a spurious separator or reset this cross-file state).
    - A single AFTER-context line larger than the 512 KiB per-group context budget — but still within the separate, larger 1 MiB per-line cap — is still printed in full, not silently dropped with no error at all; the budget only bounds how much MORE context keeps accumulating within one already-large group, mirroring `-B`'s own before-context sliding window, which has never dropped its newest line regardless of that line's own size (it only evicts OLDER lines to make room). A MATCH line falling inside an already-open trailing-context window past `-m`'s limit is ALWAYS printed regardless of the accumulated budget, even when an EARLIER, individually ordinary-sized context line in the SAME window has already exhausted that budget on its own (an earlier version of this fix only handled a single oversized line, not an accumulated total from several smaller ones) — verified directly: with `-A2 -m1`, a match, a 700 KiB non-matching line, and another match, all three lines are printed, matching real ripgrep exactly; only ORDINARY context lines (not genuine matches) remain gated by the accumulated budget. Real ripgrep has no such per-group byte cap at all and always emits a large context/match line in full.

  - **Binary-file detection:**
    - The binary-detection probe window is 64 KiB, matching ripgrep exactly (not the smaller 32 KiB window `grep` uses), so a NUL within the first 64 KiB fully suppresses a discovered file's output while a NUL beyond that falls back to reporting whatever already matched, exactly as ripgrep does for both discovery sources at that boundary.
    - A file discovered by recursively walking a directory operand is silently skipped the moment it looks binary within that probe window (no match, no notice), while an explicitly named file or stdin operand still reports the match via the binary-file notice.
    - Naming a file directly always keeps this explicit-file behavior even when a directory operand given before or after it also reaches the same file.
    - Every binary-file notice ("binary file matches (found \"\\0\" byte around offset N)" for an explicit file/stdin operand, or "WARNING: stopped searching binary file after match (found ...)" for a directory-discovered file whose NUL is found only mid-scan, after an earlier match) is written to STDOUT, matching ripgrep exactly (not stderr — verified directly: `rg abc bin.dat | wc -l` reports 1 with real ripgrep), and includes the exact byte offset of the first NUL found.
    - A directory-discovered file whose NUL is found only DURING scanning (not caught by the initial 64 KiB probe) is fully silenced in `-c`/`--files-without-match` mode — reporting nothing for that file at all, discarding any match already counted from lines before the NUL — while plain line-output mode still prints that earlier match plus the WARNING notice, and `-l` is unaffected whenever its own "stop at first match" optimization means it never reaches the NUL line to begin with.
    - An EXPLICIT file/stdin operand's binary detection, in contrast, never suppresses `-c`/`-l`/`--files-without-match` at all, only plain line-output mode.
  - **Word matching (`-w`) and case (`-S`/`--smart-case`):**
    - `-w`/`-x` resolve by command-line order when both are given (last one wins).
    - `-w` uses Unicode-aware "half boundary" matching and the SAME complete Unicode word-character definition that includes combining marks and connector punctuation (not just letters/digits/`_`) — only the context immediately outside the match is checked (non-word or start/end of line on each side), not whether the match's own first/last character is itself a word character, so e.g. `-w -e -2` matches `-2` inside `(-2)`. A boundary-rejected candidate DOES still let an OVERLAPPING candidate starting at a different (later) position within its own span be found and retried, matching ripgrep exactly (e.g. `-w 'a-b|bX'` against `a-bX ` matches only `bX`, not the rejected `a-b`, since Go's regex engine's own leftmost match at the '`a`' position is retried starting just past it rather than being skipped past entirely). When the leftmost regex match at a given START POSITION has a VALID left boundary but fails ONLY its right boundary, an alternative branch (or a longer/shorter length of the same quantified sub-pattern) starting at that exact same position IS retried, up to a bounded cumulative byte budget SHARED across every retry attempt for the whole line (a DoS-safety cap bounding total work regardless of how many positions along a pathological line are rejected, not just a per-candidate attempt-count cap, which alone is insufficient — confirmed as a real, severe gap directly: a per-call-only cap still permitted roughly one expensive retry call per CHARACTER POSITION along a huge rejected run, compounding into a multi-second-to-unbounded hang) — matching real ripgrep exactly (e.g. `-w -o -e 'a|ab'` against `ab ` rejects the leftmost `a` (the following `b` fails the right boundary) and retries the longer `ab`, which passes; `-w -c -o '-*'` against `-a` finds the greedy 1-dash match, rejects it (the following `a` fails the right boundary), retries the empty string at that same start, and reports count 1). When the pattern has genuine top-level alternation, branches are retried in their ORIGINAL TEXTUAL ORDER, not ordered by resulting match length (verified directly: ` a-b ` with `-w -o -e 'a.|a..|a'` prints `a-b` — matched via the SECOND alternative `a..` — not `a`, the shortest, LAST alternative, which a length-only retry ordering would wrongly prefer); this also applies across multiple `-F` fixed-string `-e` patterns, retried in the order given (verified directly: `-F -w -o -e 'a-' -e 'a-b' -e 'a'` against `a-b ` prints `a-b`, the SECOND pattern, not `a`, the shortest/last). When a branch itself contains its OWN quantifier (e.g. `-*`), rejecting that branch's longest exact-match length still retries OTHER lengths of that SAME branch before moving on to the next alternative, not just a single length per branch (verified directly: `-w -o -e '-*|z'` against `-----a` prints `----`, the 4-dash backtrack within the `-*` branch itself, before the `z` branch is ever tried) — the retry DIRECTION within a branch depends on whether it contains a LAZY quantifier (e.g. `.*?`): a lazy branch retries progressively LONGER lengths starting from its own shortest satisfying one, the opposite of a greedy branch's longest-first preference (verified directly: `-w -o -e 'a.*?|z'` against `ab ` prints `ab`, not `ab ` with the trailing space, since the lazy `.*?` only extends as far as needed to satisfy the right boundary rather than jumping straight to the greedy/longest extent). An UNSCOPED inline flag group (e.g. `(?i)`, as opposed to the SCOPED `(?i:...)`) applies from its own position to the end of the enclosing expression, exactly like standard regex semantics, so it is propagated forward to every LATER alternative split out for this retry mechanism too, not just the branch it textually precedes (verified directly: `-w -o -e '(?i)a|AB'` against `ab ` prints `ab`, since the leaked `(?i)` makes the retried `AB` branch ALSO case-insensitive) — a branch BEFORE the flag group, or a later sibling under a SCOPED flag group instead, remains correctly unaffected, and a flag-REMOVAL group (`(?-i)`) is recognized and propagated the same way, correctly turning a previously-leaked flag back off for still-later alternatives (verified directly: `-w -o -e 'c.|(?i)x|(?-i)y|CZQ'` against `czq ` has no match at all, since `(?-i)` turns case-folding back off before the final `CZQ` alternative, which must then stay case-sensitive). A retry attempt also never lets an internal `^`/`\A` anchor in the pattern be re-evaluated as true at the retried candidate's own subslice start when that start is not the true start of the line, matching real ripgrep exactly (verified directly: `-w -o -e 'a.|^a'` against `x a-b` has no match at all; the `^a` branch is not retried as if the rejected `a.` match's own start, at a nonzero line offset, were the true line start). The SYMMETRIC case for a TRAILING anchor (`$`/`\z`) is handled the same way: a retry candidate's own END is also not necessarily the true end of the line, so `$`/`\z` is never re-evaluated as true at the candidate's own subslice end either (verified directly: `-w -o -e 'a.|a$'` against `a-b` has no match at all; the `a$` branch is not retried against the one-byte candidate slice `a` as if ITS end were the true line end). A candidate whose LEFT boundary is invalid, in contrast, is rejected PERMANENTLY at that start regardless of length or alternative tried, since the left boundary cannot change for any candidate length starting at the same position (e.g. `-w '-2|-2X'` against `a-2X ` never matches, since the `-` is preceded by the word character `a`, failing the left boundary for every possible candidate there — confirmed even a lone, non-alternated `-2` or `-2X` by itself independently fails the identical way). The retry only ever considers a candidate whose own START/END positions are valid UTF-8 rune boundaries, never a position mid-way through a multi-byte rune's own encoding (verified directly: `-w '.'` against UTF-8 `éa` has no match at all, since the retry never tries `é`'s own one-byte encoding PREFIX as a spurious shorter candidate). When a zero-width match must be advanced past to guarantee search progress, the advance is by one whole UTF-8 rune, not one byte, so a multi-byte character is never split mid-rune into spurious extra boundary positions (verified directly: `-w -c -o ''` on a single 4-byte emoji character reports 2 real boundary positions, not 5).
    - `-S`/`--smart-case` inspects the pattern's literal characters after accounting for regex syntax (Unicode property escapes, Perl class/anchor shorthands such as `\pL`, `\w`, `\S`, and group/flag syntax such as `(?P<name>...)` or `(?U)` do not count as uppercase; an explicit character class range such as `[A-Z]` or a literal Unicode uppercase character does; a hex-escaped literal such as `\x41` or `\x{41}` — or a Unicode escape such as `\u0041`/`\u{41}`/`\U00000041`, already translated to `\x{...}` form by the time smart-case detection runs — has its REPRESENTED rune decoded and inspected, e.g. `\x41` (which denotes `A`) counts as an uppercase literal even though the escape's own two/four/six raw characters are all lowercase-or-digit; combined with `-F`, every character including a literal backslash is inspected directly with no escape-sequence interpretation).
  - **Regex/pattern semantics and hardening limits:**
    - Each `-e`/positional pattern is compiled as its own independently scoped noncapturing group before being joined, so an inline flag such as `(?i)` in one pattern cannot leak into another.
    - The combined byte length of every `-e`/positional pattern is capped at 256 KiB before any pattern reaches the regex compiler, since Go's regexp compiler can build AST/program structures whose size grows well beyond the input pattern's own length.
    - `-m 0` ("don't search anything") is checked immediately after confirming at least one pattern was given and after glob syntax validation, but before pattern compilation or any operand is resolved/opened, matching ripgrep exactly (e.g. `rg -m0 x missing-file` exits 1, never reaching the "file not found" error resolving the operand would otherwise produce, but `rg -m0 x -g '['` still exits 2 with a glob-parse error, matching ripgrep's own validation order exactly).
    - `\d`/`\D`/`\s`/`\w` (and, standalone or after a leading `^`, `\S`/`\W`) use Unicode-aware definitions matching ripgrep's default Unicode mode, not Go's native ASCII-only ones (e.g. `\w` matches `é`, `\d` matches `٣` U+0663 ARABIC-INDIC DIGIT THREE, `\s` matches U+00A0 NO-BREAK SPACE) — `\S`/`\W` used as a member of an existing `[...]` bracket alongside another member (e.g. `[\Sx]`, or even a second occurrence of the same shorthand, e.g. `[\S\S]`) is rejected with exit 2, since Go's regex engine has no way to express "the complement of this multi-range union" as a bracket member, unlike `\D`/`\d`/`\s`/`\w`, which all translate correctly in that position. `\S`/`\W` as a bracket's SOLE content, with nothing else alongside it (optionally negated by a leading `^`), is a documented exception and IS accepted: `[\S]`/`[\W]` behave exactly like standalone `\S`/`\W`, and `[^\S]`/`[^\W]` collapse to plain `\s`/`\w` (the double negation of an already-negated set), matching real ripgrep exactly — there is no set-union/negation-composition problem at all once the shorthand is the class's only content.
    - An inline `\b`/`\B` word-boundary escape anywhere in a pattern is rejected with exit 2 (use `-w`/`--word-regexp` instead, which already applies a Unicode-aware boundary check to the whole pattern), since Go's `\b`/`\B` use ASCII-only word semantics and would silently give the OPPOSITE answer from ripgrep's Unicode-aware boundaries for patterns like `caf\b` against `café`.
    - A `\Q`/`\E` literal-quoting escape anywhere in a pattern is rejected with exit 2, matching real ripgrep exactly (its own regex engine has no such extension and rejects it as an unrecognized escape sequence), since Go's regexp compiler silently ACCEPTS `\Q...\E` as an RE2-specific extension and would otherwise match text real ripgrep considers a parse error.
    - A backslash followed by ANY decimal digit (`\0` through `\9`, or a longer digit run such as `\123`) is rejected with exit 2, matching real ripgrep's own "backreferences are not supported" error exactly, since Go's regexp compiler silently accepts a leading-zero or multi-digit run of this form as a legitimate octal character escape (e.g. `\123` would otherwise match a literal `S`, octal 0123) even though ripgrep's own regex engine treats every `\<digit>` form uniformly as unsupported backreference syntax — an escaped backslash immediately before a digit (e.g. `\\1`, a literal `\` followed by a literal `1`) is unaffected and still matches normally.
    - `\uHHHH` (exactly 4 hex digits), `\UHHHHHHHH` (exactly 8 hex digits), and the braced `\u{H...}`/`\U{H...}` forms (1-6 hex digits, `\u` and `\U` behaving identically once braced) are accepted as Unicode code point escapes, matching real ripgrep exactly (e.g. `\u0041`, `\u{41}`, and `\U00000041` all match a literal `A`), since Go's regexp compiler has no `\u`/`\U` escape syntax of its own at all — translated internally to Go's own `\x{HEX}` form. The non-braced forms consume EXACTLY the fixed digit count, leaving any additional digits as separate literal characters (e.g. `\u00041` is `\u0004`, a control character, followed by a literal `1`, not a 5-digit codepoint); a malformed escape (wrong digit count, invalid hex, or an out-of-range codepoint) still exits 2, via Go's own `\x{...}` rejection rather than ripgrep's own differently-worded parse error.
    - The combined byte length of every `-e`/positional pattern AFTER Unicode-class translation (not just the raw input length) is separately capped at 16 MiB, since `\w`/`\s`/etc.'s expansion factor (a 2-byte `\w` token becoming several KiB of explicit Unicode-property members) means the raw-input 256 KiB cap alone does not bound the translated text's size.
    - This cap is enforced INCREMENTALLY while translating each pattern (aborting the moment the translated output so far would exceed the remaining budget), not only after a whole oversized pattern has already been fully expanded into memory, so a single pattern containing many shorthand-class tokens cannot allocate hundreds of MiB before being rejected.
  - **Operand, provenance, and path-display semantics:**
    - Explicit file operands and directory-discovered files are opened through the sandbox's identity-verified `OpenRegularFile` (nonblocking, rejects descriptor portals), not a plain `OpenFile`.
    - The cumulative number of files discovered across all directory operands in one invocation is capped at 1,000,000, and the cumulative byte length of every discovered path is separately capped at 128 MiB (both independent of the per-directory `MaxDirEntriesPerLevel` cap; a warning is emitted and remaining files are not searched beyond either limit).
    - The total number of path OPERANDS (explicit files, `-` for stdin, or directories) given in one invocation is separately capped at 10,000, checked up front before any `StatFile`/traversal work begins for any of them — unlike the discovery caps above, this bounds explicit operand OCCURRENCES, which rshell deliberately does not deduplicate (see the duplicate-operand behavior below) and which the discovery caps do not otherwise bound at all. (A single shell command line cannot construct more than roughly 16,382 such operand words in the first place, per the shell's own independent, lower `MaxExpandedArgumentsPerCommand` field-expansion cap — this builtin-level cap exists as defense-in-depth for non-shell embedding paths that might bypass that shell-level enforcement.)
    - `\w`'s Unicode translation uses ripgrep's full definition (`\p{Alphabetic} ∪ \p{M} ∪ \p{Nd} ∪ \p{Pc} ∪ \p{Join_Control}`), not just `\p{L}\p{M}\p{Nd}\p{Pc}` (an earlier, narrower version of this translation used exactly that subset, which omitted Unicode's derived Alphabetic property — general category Nl, e.g. U+2167 ROMAN NUMERAL EIGHT, and a further Other_Alphabetic set — and the two Join_Control characters U+200C/U+200D, neither of which real ripgrep's `\w` omits).
    - A standalone (not inside `[...]`) `\p{Name}`/`\P{Name}` naming a Unicode binary property Go's `regexp/syntax` does not support directly (it only supports general categories and scripts) but Go's own standard library exposes via `unicode.Properties` (e.g. `White_Space`, `ASCII_Hex_Digit`, `Dash`, and 31 other such names) is translated into an explicit `\x{lo}-\x{hi}` member set wrapped in `[...]`/`[^...]` rather than rejected, matching real ripgrep exactly for every one of those names (individually verified: ripgrep accepts all of them, via Rust's own larger Unicode property table). A property neither Go's `regexp/syntax` nor `unicode.Properties` recognizes (e.g. `\p{Emoji}`, `\p{Alphabetic}` as a standalone top-level token — real ripgrep accepts both, but Go's standard library has no equivalent ready-made range table for either) remains rejected with exit 2, a documented, intentional remainder rather than a regression; an in-bracket occurrence of a translatable name (e.g. `[\p{White_Space}a]`) is also out of scope and remains rejected.
    - A POSIX character class `[:name:]` (e.g. `[:alpha:]`) used alongside a `\w`/`\d`/`\s` shorthand inside the same `[...]` bracket (e.g. `[[:alpha:]\w]`) is translated correctly in either order, matching ripgrep exactly.
    - A `\d`/`\D`/`\s`/`\S`/`\w`/`\W`/`\p{...}`/`\P{...}` shorthand used as one endpoint of an apparent `X-Y` range inside a `[...]` class (e.g. `[\d-a]`, `[a-\d]`, or `[\p{L}-a]`) is rejected with exit 2 (`invalid range boundary, must be a literal`), matching ripgrep's own regex parse error exactly, instead of being silently accepted with a DIFFERENT meaning than intended: Go's regexp compiler, unlike ripgrep, would otherwise silently reinterpret e.g. `[\p{Nd}-a]` as a UNION of the shorthand's expansion, a literal `-`, and a literal `a` — not a range, and not an error. A shorthand that merely appears near a `-` without actually forming a range (a trailing dash immediately before the closing `]`, a leading dash immediately after `[`/`[^`, or a shorthand used as a plain class member with no adjacent dash at all) is still accepted normally.
    - A directory operand always enables path prefixes for every result, even when that directory itself yields zero searchable files (empty, or fully filtered by `-g`) and only an explicit file operand ends up being searched.
    - Naming a file directly always keeps its explicit-file binary-match reporting even when a directory operand given before or after it in the same command also reaches the same file.
    - An operand named more than once (an explicit file, or a file reachable from two different directory operands) is searched and reported once per occurrence — operands are never deduplicated.
    - A directory operand's original spelling (not a cleaned/joined path) is prepended to every path discovered beneath it in filename-bearing output, matching ripgrep exactly (e.g. `rg -H x .` on a file at `sub/f` prints `./sub/f:x`, keeping the leading `./`; `rg -H x sub/.` prints `sub/./f:x`, keeping the redundant `/.`), and an explicit file operand's display path is likewise the operand exactly as given, never cleaned (e.g. `rg -H x a/../f` prints `a/../f:x`) — except when no path operand was given at all (the implicit `.` default), which shows no `./` prefix whatsoever, unlike an explicitly typed `.` operand (verified directly: bare `rg needle` prints `top.txt:needle`, while `rg needle .` on the same tree prints `./top.txt:needle`).
    - On Windows, a directory operand's own spelling is preserved verbatim as above, and a NEWLY inserted separator between it and a discovered child (i.e. when the operand itself had no trailing separator) still defaults to `/` — exactly like every other platform — UNLESS the operand was itself spelled with a `\` somewhere, in which case the newly inserted separator is `\` too, so a `\`-spelled operand (e.g. `C:\root`) gets consistently `\`-joined children (`C:\root\child`) rather than a mixed `C:\root/child`; an EXISTING trailing separator, spelled with either `/` or `\`, is still never touched (same "no further cleaning applied" rule as above).
    - Binary-file provenance (discovered-by-traversal vs. explicit) is tracked per OCCURRENCE, not per path, so a path reached by both an explicit operand and an overlapping directory operand in the same command (e.g. `rg needle dir/f dir`) reports its binary match exactly once — from the explicit occurrence — regardless of operand order, rather than either reporting it twice or losing the explicit-file semantics entirely.
    - `-c` counts individual matched substrings (not selected lines) when combined with plain `-o` (not `-o -v`, which has no substring to isolate), matching ripgrep exactly, while `-m` still caps the number of matching lines processed rather than the number of individual matches a `-c -o` count may enumerate per line.
    - `--files` is capped the same way as a search and additionally honors `-q` (no listing output), and its own listing loop checks the shell's execution context on every iteration (mirroring the search loop), so a canceled/expired context stops emitting further already-discovered paths rather than writing every retained path from a large partial traversal result regardless of the deadline.
    - `--files -q` (whose only observable output is the exit status) stops LISTING after finding the FIRST eligible file, matching ripgrep exactly, but every operand's own existence/readability is still validated and reported to stderr regardless of operand order — only the expensive full listing/traversal of an operand given after the first eligible file is skipped, not its existence check; `-q` without `--files` (ordinary content search) behaves the same way: content search of a later operand stops once an earlier operand already matched, but a later operand's own path error is still reported. The exit status reflects only whether at least one file/match was found, ignoring any error on any operand (match/found-file > error > not-found priority); without `-q`, in contrast, an error on any operand still forces exit 2 regardless of other operands' success.
    - A content search's own `-q` (not just `--files -q` above) likewise interleaves discovery with searching, at TWO levels: one path operand at a time (stopping CONTENT SEARCH the moment any file matches, rather than fully searching every operand up front), and, within a single directory operand's own traversal, one discovered file at a time (searching each file the instant it is found during traversal, rather than fully discovering and sorting the whole subtree first) — every operand's own existence/readability is still validated and its error (if any) reported to stderr regardless of whether it comes before or after the matching operand, matching real ripgrep exactly (only the expensive content search of a later operand is skipped once a match is already found, not its own existence check), while a match anywhere still wins over an error anywhere else in the final exit code, matching ripgrep's exit-code priority exactly.
    - `-o`'s per-line match enumeration (both plain `-o` output and `-c -o` counting) checks the shell's execution context before every individual match, not just once per line, so a single line matching at (or near) every byte position cannot enumerate an unbounded number of matches — and, for `-o`, perform that many stdout writes — before a canceled/expired context is noticed.
    - A `^`/`\A` (start-of-text/start-of-line) anchor in a pattern combined with `-o` is evaluated only against the TRUE start of a line, not re-evaluated as satisfied at every position `-o`'s own per-match streaming search resumes from (e.g. `rg -c -o '^a'` against `aaa` reports 1, matching real ripgrep exactly, not 3), while an anchor combined with an unanchored alternative in the same pattern (e.g. `^a|b`) still lets the unanchored branch keep matching normally at every later position (e.g. `rg -c -o -e '^a|b'` against `ababab` reports 4: the anchored `a` once, plus all three `b`s).
    - When stdin is used as an operand (`-` or the implicit default with no path given) and is a pipe or other source that can block indefinitely without supplying data, the initial binary-detection probe read against it still respects the shell's own execution deadline rather than blocking forever regardless of cancellation. This cancellable-read handling applies to every opened reader, not merely stdin: a regular file backed by a stalled network/FUSE filesystem (or a custom embedder's own blocking reader substituted for the regular-file-open capability) is likewise interrupted once the deadline fires, rather than relying solely on closing the underlying descriptor — reliable for ordinary pollable file descriptors, but not a portable cancellation mechanism for a truly synchronous, blocking kernel read. When the reader is backed by a real OS file descriptor supporting a kernel-level read deadline (as stdin itself is, when it is a pipe), that cheaper mechanism is used directly rather than always falling back to a goroutine-based cancellation path.
    - `-c -o`'s count (and plain `-o`'s own per-match output) never reports a zero-width match sitting at the exact position where an immediately preceding NON-EMPTY match just ended, matching both Go's own `regexp.FindAllIndex` and real ripgrep exactly (e.g. a lone `x` against pattern `x*` counts as 1 match, not 2, since the zero-width match immediately after the non-empty `x` match is suppressed) — a zero-width match that is NOT adjacent to a preceding non-empty match (e.g. a genuine end-of-string zero-width match unrelated to any earlier match's own end) is still reported normally. This same suppression applies under `-w`/`--word-regexp` too (e.g. a lone `-` against pattern `-*` under `-w -c -o` counts as 1, not 2), since a zero-width candidate at that same adjacent position independently passes the half-boundary check (which only inspects the context OUTSIDE the candidate, with no way to know an earlier match already claimed that exact position) and needs its own, separate suppression from the non-word-mode case above. Outside `-w` (a plain, non-word pattern), a zero-width match is advanced past BYTE-wise, not rune-wise, matching real ripgrep exactly: `-c -o ''` against UTF-8 `éa` (`\xc3\xa9a`, `é` a 2-byte-encoded rune) reports 4 — a zero-width match at every byte offset, including the one INSIDE `é`'s own 2-byte encoding — not 3, which rune-wise advancement would wrongly produce by skipping that mid-rune offset entirely. `-w`'s own advancement remains rune-wise (see its own bullet above), since `-w`'s half-boundary check must never resume mid-rune. Once the non-word search resumes at a byte position landing INSIDE a multi-byte rune's own encoding, however, a NON-EMPTY match is never allowed to start there (only a trivial always-matching-empty candidate can, matching ripgrep's own byte-wise-but-char-boundary-aware behavior exactly): `-c -o '^|.'` against the same UTF-8 `éa` reports 2 (an empty match at position 0, then `a` at position 2), not 3, since a non-empty `.` match is never permitted to spuriously consume the invalid continuation byte at position 1.
    - Stdin's filename-bearing output uses `<stdin>`, matching ripgrep's own label, not `grep`'s POSIX-style `(standard input)`.

## Pipes and Redirections

### Always supported (both modes)

- ✅ `|` — pipe stdout
- ✅ `<` — input redirection (read-only, within AllowedPaths)
- ✅ `<<DELIM` — heredoc
- ✅ `<<-DELIM` — heredoc with tab stripping
- ✅ `2>&1`, `>&2` — file descriptor duplication between stdout (1) and stderr (2)
- ✅ `> FILE`, `>> FILE` — write/truncate or append to a regular file; **remediation mode only**, target must be within a `:rw` `AllowedPaths` root (exit 1 otherwise)
- ✅ `2> FILE`, `2>> FILE` — same rules applied to the stderr stream; **remediation mode only**
- ✅ `&> FILE`, `&>> FILE` — redirect both stdout and stderr to the same file; **remediation mode only**, same `AllowedPaths` enforcement
- ❌ `|&` — pipe stdout and stderr (bash extension)
- ❌ `<<<` — herestring (bash extension)
- ❌ `<>` — read-write open (blocked in all modes)
- ❌ `<&N` — input file descriptor duplication

For a simple command, rshell expands only enough words to identify the command, then applies `AllowedCommands`, selective-elevation, and remediation-mode policy before expanding the remaining arguments, inline assignments, or redirects. A rejected command therefore cannot run command substitutions from unused arguments, read or expand a heredoc, or read, create, append to, or truncate a redirect target. Redirect-only statements remain authorized by the applicable mode and `AllowedPaths` policy. After authorization, redirects follow normal shell timing: they are established before command execution, so an authorized command that later exits nonzero can still create or modify its redirect targets.

### Output redirections (mode-dependent)

| Redirect | read-only mode | remediation mode |
|----------|---------------|-----------------|
| `>/dev/null`, `2>/dev/null`, `&>/dev/null` | ✅ always accepted (discards output) | ✅ always accepted |
| `>>/dev/null`, `&>>/dev/null` | ✅ always accepted (same effect as truncate) | ✅ always accepted |
| `> FILE`, `>| FILE` | ❌ exit 2 (parse-time rejection) | ✅ within `:rw` `AllowedPaths`; exit 1 outside or in read-only roots |
| `>> FILE` | ❌ exit 2 | ✅ within `:rw` `AllowedPaths`; exit 1 outside or in read-only roots |
| `2> FILE` | ❌ exit 2 | ✅ within `:rw` `AllowedPaths`; exit 1 outside or in read-only roots |
| `2>> FILE` | ❌ exit 2 | ✅ within `:rw` `AllowedPaths`; exit 1 outside or in read-only roots |
| `&> FILE` | ❌ exit 2 | ✅ within `:rw` `AllowedPaths`; exit 1 outside or in read-only roots |
| `&>> FILE` | ❌ exit 2 | ✅ within `:rw` `AllowedPaths`; exit 1 outside or in read-only roots |

The `exit 2` rejections above apply to a **literal** target, which the validator
can resolve before the script runs. A target that is not a plain literal —
`> "$F"`, `> $F`, `> "/dev/null"` — is not resolved at validation time (the
validator never expands user input); it is checked at run time against the
expanded value instead. In read-only mode the policy is identical (only
`/dev/null` is accepted), but the failure mode is gentler: that single command
fails with exit 1 and the script continues, rather than the whole program being
rejected with exit 2. So `F=/dev/null; echo x > "$F"` succeeds, and
`F=out.txt; echo x > "$F"` prints
`> out.txt: file redirection is only supported for /dev/null` and fails just
that command. A command substitution in the target (`> $(cmd)`) is the one
dynamic form still rejected with exit 2, so that a blocked redirect never runs
the substituted command.

## Execution

- ✅ AllowedCommands — allowlists names in the `rshell:` namespace (e.g. `rshell:cat`); registered commands may execute, while allowlisted unknown names still fail with exit code 127; if not set, no commands are allowed
- ✅ AllowedSystemServices policy — one shared default-deny capability map for exact unit names with `read`, `clean`, `start`, `stop`, `reload`, `restart`, `enable`, and `disable` actions; the `*` action wildcard grants every action supported by the running and future rshell versions for its exact unit and is expanded in `help`; actionless grants are ignored, invalid names/actions are skipped, names are case-sensitive, are not normalized, and cannot contain `:` or globs; all valid unit types are accepted; `read` remains usable by bounded `journalctl` queries in read-only mode, every non-read action requires remediation mode, and the entire `systemctl` builtin separately requires remediation mode while `list-units` sees only exact `read` grants; allowing all commands does not bypass this policy; a `read` grant on a `.slice` unit is the one selector whose journal results are not bounded by the granted name, because `journalctl -u SLICE` matches `_SYSTEMD_SLICE` and therefore returns every entry logged by every unit in that slice (see the trusted systemd target exception in `docs/RULES.md`); configure grants through `interp.AllowedSystemServices` or CLI `--allowed-services UNIT:ACTION[+ACTION...]`
- ✅ SystemdTargetConfig — systemd-aware builtins use standard local paths by default; explicit `JournalDirs`, `MachineIDPath`, `JournalControlSocket`, and `ManagerBusSocket` paths support container mount layouts without falling back to local endpoints; target paths are trusted configuration and bypass `AllowedPaths`; explicit mounts must all refer to the same host; manager operations use the public system D-Bus socket (default `/run/dbus/system_bus_socket`), pin its inode, authenticate, and verify the systemd manager peer's machine ID, while the private `/run/systemd/private` endpoint is unsupported
- ✅ AllowedPaths filesystem sandboxing — restricts all file access (read and write) to specified directories. Entries may end with `:ro` or `:rw` to indicate read-only and read-write permissions, respectively; entries without a suffix default to read-only. In remediation mode, write operations are accepted only inside the most-specific matching `:rw` root. Cross-root symlink fallback is read-only to avoid TOCTOU on writes; on Unix, symlink components in write targets are rejected with `symlinks are not supported as write targets` via a no-follow `openat` walk. Containment is path-based and cannot see hard links, so on Unix every content-mutating write target is additionally `fstat`ed after open and rejected with `hard links are not supported as write targets` when its link count exceeds one; `rm` is deliberately exempt (unlinking one of several names changes no content). Not enforced on Windows, where no link count is available from an open handle
- ✅ Whole-run execution timeout — callers can bound a `Run()` call via `context.Context`, `interp.MaxExecutionTime`, or the CLI `--timeout` flag; the deadline applies to the whole script. Cancellation is checked between bounded operations; a caller-owned stream blocked in `Read` or `Write` can delay return because rshell does not close borrowed streams
- ✅ ProcPath — overrides the proc filesystem path used by `ps` (default `/proc`; Linux-only; useful for testing/container environments); `ps` reads only bounded process metadata and counters, never `/proc/<pid>/cmdline` or process environment data
- ✅ RemediationMode — opt-in mode (`interp.WithMode(interp.ModeRemediation)` / `--mode remediation`) that enables file-target output redirections (`>`, `>>`, `2>`, `&>`, `&>>`) within `:rw` `AllowedPaths` and remediation-only builtins such as `truncate`, `logrotate`, `rm`, and the entire restricted `systemctl` surface; targets outside the allowlist or inside read-only roots fail with `permission denied` (exit 1); symlinked write targets fail with `symlinks are not supported as write targets`; hard-linked write targets fail with `hard links are not supported as write targets` on Unix; `/dev/null` always accepted; `<>` remains blocked
- ✅ Privileged helper isolation (Linux) — authenticated `runCommand` and `runRemediationCommand` Private Action Runner dispatches run in fresh same-binary workers with a Landlock ABI 3+ policy derived from the verified effective `AllowedPaths`, `AllowedCommands`, and `AllowedSystemServices`, followed by a TSYNC seccomp denylist; authorized `journalctl` and remediation-mode `systemctl` calls receive only the fixed local systemd paths their grants require; `runCommand` forces ordinary path grants to read-only and never grants journal deletion rights, verified roots are pinned before execution drops back to the service account, sandbox setup fails closed, external execution is denied, and only explicitly authorized commands use controlled `setresuid` elevation
- ❌ External commands — unavailable through the stock runner because it exposes no external-command executor; allowlisting an unknown name does not make it executable
- ❌ Background execution: `cmd &`
- ❌ Coprocesses: `coproc`
- ❌ `time`
- ❌ `[[ ... ]]` extended test expressions (bash extension)
- ❌ `(( ... ))` arithmetic commands
- ❌ `declare`, `export`, `local`, `readonly`, `let`

## Intentional Divergences

- **Time reference for `find -mmin`/`-mtime` and `ls -l`**: rshell captures `time.Now()` once at the start of each `Run()` call and shares it across all builtins in that run. Bash evaluates each command against its own invocation time. In practice this only matters for long-running scripts (e.g. `sleep 61; find . -mmin -1`) where the reference time drifts from the actual command start. Short-lived AI agent scripts are unaffected.
- **`jq` number model**: integer literals and integer-only `+`, `-`, `*`, `%`, and exact division remain exact up to 256 bits; larger values are reported and skipped. Decimal/exponent literals, mixed arithmetic, and non-integral division use `float64`, so integer arithmetic does not preserve signed zero. The integer bound prevents unbounded `big.Int` growth under chained multiplication.
- **`jq` floating-point rendering**: decimal/exponent values are stored as `float64`, so output is normalized instead of preserving source spelling. Overflow saturates to `±1.7976931348623157e+308`; underflow becomes `0`.
- **Strict JSON input in `jq`**: leading-zero numbers and raw NUL in strings are rejected instead of reproducing jq's permissive or chunk-dependent behavior. An unpaired low surrogate (`"\udc00"`) decodes to U+FFFD; an unpaired high surrogate is an error.
